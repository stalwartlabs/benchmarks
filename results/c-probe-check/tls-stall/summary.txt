# TLS stall check on bench-c10-1026 (idle cluster, 2026-10-26 ~06:47Z, w1)
Method: on load1, tcpdump -i any -nn -tt -w (host SERVER and port 25) while 5 sequential single sessions ran `openssl s_client -starttls smtp -quiet` with EHLO after 1 s and QUIT after 2 s more (OpenSSL 3.0.13, TLS 1.3), against Dovecot's Postfix (10.10.0.6) then Stalwart (10.10.0.5). Pcaps: c10-dovecot.pcap, c10-stalwart.pcap (the -i any capture lists every packet twice; analyze.py dedupes). Parse: analyze.py (python3 -I analyze.py).
Result: no stall on either side. After every client data segment the next server data segment follows within 0.04-0.3 ms:
 - STARTTLS command (10 B) -> `220 2.0.0 Ready to start TLS` (30/31 B): 0.04 ms both.
 - TLS ClientHello (293 B) -> ServerHello..Finished (1293-1295 B Postfix/Dovecot, 1228-1229 B Stalwart): Postfix 0.21-0.30 ms, Stalwart 0.11-0.21 ms.
 - client Finished + EHLO (80 B) -> server segment 287 B (Postfix) / 184 B (Stalwart): Postfix 0.15-0.23 ms, Stalwart 0.05-0.07 ms.
 - QUIT (45 B) -> 192 B (Postfix) / 217 B (Stalwart): 0.10-0.12 ms (Postfix), 0.10-0.14 ms (Stalwart); close alert 28 B -> 37/38 B: 0.09-0.12 ms.
The ~1 s and ~2 s gaps in the server-to-server table are the client-side sleeps of the test script, not server stalls. Between consecutive server segments the client's pure ACK is present (ack-between) where the client had not sent data itself; where "no-ack" is printed the client answered with a data segment instead. In all 10 sessions the client ACK of the server TLS data precedes (or coincides with) the next server segment; the TLS ticket/Finished segment and the following reply are never separated by a delayed-ACK gap (no 40 ms or 200 ms gaps seen).
Limits: idle servers, one session at a time, so this does not reproduce the loaded conditions of the 16x10 cell.
