# Caveats and known limits

Part of the Stalwart vs Postfix and Dovecot comparison. Start at the [README](../README.md).

This page lists everything a reader needs to know to interpret the results correctly: where the comparison is not perfectly symmetric, where a number is a bound rather than an exact value, and where a system behaves in a way that dominates a test.

## 1. Postfix's 40 ms stall after the TLS handshake

On about 73% of Postfix TLS connections (in a packet-capture diagnostic on one cluster, [results/c-probe-check/tls-stall/c20/](../results/c-probe-check/tls-stall/c20/)), the first reply after the handshake arrives about 40 ms late, because Postfix sends the TLS session ticket and its reply as two small segments without `TCP_NODELAY` and the client's delayed ACK holds the second one back. It affects every Postfix SMTP test (receiving, submission, relaying, delivery and the sustained SMTP rates); IMAP is not affected. Clients with the default Linux TCP stack see it; a client that acknowledges immediately does not. All factors in this report are end to end and include it. The cause and its source references are in [RESULTS.md](RESULTS.md#postfixs-40-ms-stall-after-the-tls-handshake).

## 2. Dovecot IDLE falls back to a 30 s poll after an index log rotation

With mdbox, Dovecot's IDLE watches the mailbox index log. Our reading of the Dovecot source is that after the log rotates, the watch stays on the old file and IDLE falls back to its 30 s periodic check until the client issues IDLE again; this is inferred from the source, not confirmed on the test systems, whose on-disk state from the test window could not be inspected afterwards. In the IDLE test about 44% of Dovecot's samples took 30 s, so its p90 and p99 are 30 s and it completed 133 of the planned 500 samples within the 30-minute run limit. Its p50 (the fixed 500 ms notification delay plus about 1 ms) is the representative value. Details in [RESULTS.md, section 2](RESULTS.md#2-c2-smtp-to-inbox-delivery-latency).

## 3. Durability is not identical

Stalwart (as shipped) and Dovecot (`mail_fsync = never`) acknowledge writes without an fsync; Postfix always fsyncs its queue file before the 250 and cannot be configured not to. SMTP results therefore favour Stalwart by an amount that was not measured. A Dovecot variant with `mail_fsync = always` is published for the write tests. See [FAIRNESS.md, section 1.1](FAIRNESS.md#11-durability-this-favours-stalwart).

Some Dovecot latencies of about 1 s come from its full-text indexing, not from storage. We set `fts_autoindex = yes`, so that Dovecot indexes new mail on arrival as Stalwart does; a stock Dovecot install does not see this, because full-text search is off by default and `fts_autoindex` defaults to `no`. After a COPY, MOVE or APPEND, Dovecot's indexer process holds the write lock on the mailbox's fts-flatcurve (Xapian) index while it indexes the new messages. An EXPUNGE or MOVE that arrives in the meantime must update the same index; when it finds the index locked, fts-flatcurve sleeps a fixed 1 s and retries (a compile-time constant, up to 60 times), while the imap process keeps the mailbox locked. A system-call trace on one cluster confirmed this sequence. It shows as a Dovecot p50 of 1.01 to 1.05 s, whatever the number of messages, in the single-session MOVE and EXPUNGE tests where the operation closely follows an untimed step that saved new messages into the mailbox (the setup or undo of the preceding sample): MOVE of 10% of a mailbox (c14-sessions1-move-10p, default and `fsync=always`), MOVE of 100 messages (c14-sessions1-move-range100, `fsync=always`) and EXPUNGE of 100 messages (c15-sessions1-range100-uid_false and -uid_true, `fsync=always`). With the default settings, the same wait shows in the tail of several single-session tests (p95 and p99 of c14-sessions1-move-one and -move-range100, p99 of c15-sessions1-range100-*, p95 of l14-copy-move-large10k-move-range100). As a diagnostic, not a published result, MOVE of 10% on one session was run on the same cluster with `fts_autoindex = no`: Dovecot's p50 fell from about 1,076 ms to about 20 ms. The published values are as measured with indexing on, which is the configuration both systems are compared in; the p50 values near 1 s are marked in the RESULTS tables, and none of them enters the README summary, the headline factors, the tally or the charts.

## 4. Throughput: lower bounds, saturation and acceptance

- **Lower bounds.** When a system still met the SLO at the top step of its rate ladder, the ladder was continued with the same step timing and SLO (`scenarios/c-ext/`). A rate that still met the SLO at the very top is published as ">=", and a factor computed from it as "at least".
- **Saturated steps.** The ladder stops one step after the second consecutive SLO miss. When that last step drops arrivals because the server stopped keeping up (the generator's in-flight limit fills up behind the server, while generator CPU stays low and no arrival is late), it marks saturation and does not invalidate the run. A run is invalid only when the generator limited a step at or below the reported rate.
- **Acceptance.** Throughput counts SMTP acceptance (the 250 after DATA) on both systems. Delivery into the mailbox follows from each server's queue; every run starts with drained queues, and no message bounced or was lost. At the highest rates, Dovecot's per-user LMTP concurrency limit (default 10) made Postfix defer a few deliveries, which were retried and delivered.

## 5. 10-messages-per-connection test

This load test opens connections at a rising rate and sends 10 messages on each. The plan's SLO (p99 at most 1 s, at most 0.1% errors) applies to each message inside the session, so it does not count failed sessions. At high rates both systems fail sessions while their per-message latency still meets the SLO: from 1,525 connections/s on, Stalwart answers MAIL FROM with SMTP 452 (its memory-based backpressure at shipped defaults) on a growing share of sessions (35% at 1,525 connections/s, 88% at 4,183/s, in one repetition) while it keeps accepting about 10,000 messages/s, and Postfix reaches its smtpd process limit (1,000, the tuned value), so connections wait seconds for a greeting or time out (erratically, up to 42% of sessions in a step from 202 connections/s on). The steps without failed sessions already have whole-session p99 values of seconds on both, and the highest of them come from single repetitions. No single number describes this test honestly, so it is left out of the headline comparisons; [RESULTS.md, section 3](RESULTS.md#3-c3-smtp-inbound-throughput) shows every step for both systems.

## 6. State accumulation in Dovecot's mdbox

Between repetitions, the 1 MB SMTP tests, the SMTP throughput tests and the EXPUNGE tests on regular mailboxes get an untimed, symmetric cleanup on both systems (load-test messages deleted over IMAP, plus `doveadm purge -A` on Dovecot). No other test does. Stalwart reclaims the space of deleted messages at its scheduled purge, so between repetitions it still holds them on disk; that does not change what the next run reads or writes.

The tests that move or expunge 10% of a large mailbox are not cleaned up, because that would need the large account restored between repetitions. In four of them Dovecot's latency drifts between repetitions (mostly upwards), because mdbox keeps moved and expunged messages in its storage files and index logs until `doveadm purge`: MOVE of 10% on the 100k and 250k mailboxes, and UID EXPUNGE of 10% on the 10k and 250k mailboxes. Stalwart changes much less. The winner and the order of magnitude do not change.

Some cleaned-up tests drift as well. In the SMTP inbound throughput test (c03, cluster c19), Postfix + Dovecot's highest rate that met the SLO fell from one repetition to the next (723.1, 263.5 and 188.2 messages/s), while Stalwart reached the top of the ladder in every repetition. In some EXPUNGE tests on regular mailboxes, Dovecot's latency rose with each repetition while Stalwart's stayed flat (the list is in [RESULTS.md, section 14](RESULTS.md#14-flags-cv-errors-incomplete-cells)). The cause is state accumulating on the Dovecot side that the per-repetition cleanup (load-test messages deleted over IMAP, then `doveadm purge -A`) does not remove. Dovecot ran with `fts_autoindex = yes` and the flatcurve backend, and its full-text index kept growing across repetitions although the messages were removed between them: after the three c03 repetitions, the full-text index of the regular users was 11.2 GiB, against 1.8 GiB on a cluster whose regular users were never written to (6.3x), while their index logs were 1.46x and index caches 1.78x the untouched size. This is the likely cause of the falling Postfix + Dovecot results (the same index also causes the 1 s lock waits described in section 3), but it is not confirmed: running `doveadm fts optimize` or other index maintenance between repetitions was not tested, so it is unknown whether it would remove the drift.

A test counts as drifting when one system's result moves in the same direction in every repetition, by 10% or more from the first to the last. Where drifting tests appear in the README, the factor comes from the repetition least favourable to Stalwart (usually the first; a later one where Dovecot got faster across repetitions), followed by the median over the reported repetitions; [RESULTS.md, section 14](RESULTS.md#14-flags-cv-errors-incomplete-cells) lists every drifting test with its per-repetition values. The tables show the median as for every other test. A check of every other test for results that drift with the repetition order found nothing beyond normal noise.

## 7. Time caps reduce some sample counts

Every run has a time limit (20 minutes for the large-mailbox tests, 30 minutes otherwise). Where Dovecot is slow enough to reach it, it completes fewer samples than planned, and the "Samples" column shows the real count per system:

- MOVE of 10% takes Dovecot about 12 s per operation on the 100k mailbox and 32 to 34 s on the 250k mailbox (p99 up to 48 s), plus an untimed setup per sample, and UID EXPUNGE of 10% is similarly slow, so these tests have fewer samples than the planned 50 (for example 28 for Dovecot's first repetition of MOVE).
- MOVE of 100 messages: Dovecot completed about 4,400 to 5,000 of the planned 10,000 samples per repetition, because a share of its MOVEs take about 1 s.
- IDLE: 133 of 500 samples ([section 2](#2-dovecot-idle-falls-back-to-a-30-s-poll-after-an-index-log-rotation)).

## 8. Clusters, network symmetry and repetitions

The tests ran on many identical clusters in parallel, each a full copy of the setup in its own Azure region. Within a test, both systems and all repetitions run on one pair of server VMs from the same load hosts; tests of one family (for example SMTP receiving at different sizes, or the EXPUNGE tests) may come from different clusters, and every table names the cluster in its "Pair" column. The exceptions within a test are the Dovecot `fsync=always` variants of the two inbound throughput ladders (c03 on c20, the continuation of c03-mpc10 on c16), which ran on a different VM pair from the two main systems. Factors that use a ladder continuation for one system and the original ladder for the other also cross VM pairs: the mixed IMAP capacity (Stalwart's continuation on c26, Postfix + Dovecot on c6). The tables mark every continued value with its cluster.

Network symmetry rule: on every cluster, the p50 round trip from each load host to Stalwart and to Dovecot, and from each server to the sink, should differ by no more than 10 us ([METHODOLOGY.md, section 1.2](METHODOLOGY.md#12-clusters-and-network-symmetry)). Three clusters ended outside it:

- **c12, 26.2 us** (load1 to Stalwart 52.5 us, to Dovecot 78.7 us). It ran one test, MOVE of 10% of an INBOX with one session (c14-sessions1-move-10p). Dovecot needs about 1 s per MOVE there and Stalwart about 0.3 ms, a factor in the thousands; a few tens of microseconds per round trip cannot change that.
- **c16, 22.0 us** maximum difference, on the server-to-sink leg; on the load-host legs, the only ones the 10-messages-per-connection test uses, the differences are 14.3 us (load1) and 12.9 us (load2). It ran only the Dovecot `fsync=always` continuation of the 10-messages-per-connection ladder, which uses no sink and whose SLO is a p99 of 1 s; that variant is compared across VM pairs anyway.
- **c20, 11.5 us** (load1 to Stalwart 75.5 us, to Dovecot 64.0 us). It ran only the Dovecot `fsync=always` variant of the inbound throughput ladder, with the same p99 1 s SLO, also compared across VM pairs.

Each result is the median over its repetitions (3 for most tests, 2 for large mailboxes with a warm cache, 10 one-sample repetitions for cold cache). Tests whose repetitions still spread by more than 10% (coefficient of variation above 0.10) after one automatic rerun are listed in [RESULTS.md, section 14](RESULTS.md#14-flags-cv-errors-incomplete-cells).

## 9. Reduced test set

256 of the 348 planned tests ran: one IDLE test instead of twelve, the `fsync=always` variant only on write tests, 2 repetitions for large mailboxes with a warm cache, and five operations with a cold cache ([METHODOLOGY.md, section 2.7](METHODOLOGY.md#27-reduced-cell-set)).

## 10. Build and configuration differences

- Stalwart is compiled for the exact CPU (Zen 5) with rustc 1.98.0 (the newer 1.99.1 crashes inside LLVM on this build); Postfix and Dovecot are generic x86-64 builds as distributed ([METHODOLOGY.md, section 1.4](METHODOLOGY.md#14-stalwart-build)).
- Four Stalwart builds appear in the tables, all with the same release flags: `f976519d` for every unmarked row, `2d80f00b` for the rows marked ‡ (warm STORE on large mailboxes and five STORE tests on regular mailboxes), `8b3d762a` for the rows marked § (three APPEND tests) and `a665cdfa` for the rows marked ¶ (three SELECT QRESYNC tests, 3 runs per system). Marked rows have fewer repetitions than the main protocol: 2 Stalwart and 4 Postfix + Dovecot runs for large-mailbox STORE, 1 run per system for the regular-mailbox STORE tests and the 16-session 4 KB APPEND test, 2 runs per system for the 64 KB APPEND tests. Postfix + Dovecot were measured in the same session as Stalwart for every marked row.
- The rows marked § ran on cluster c8, while their `fsync=always` column comes from cluster c6, so their Pair column reads "c8+c6" ([METHODOLOGY.md, section 1.4](METHODOLOGY.md#14-stalwart-build)).
- Stalwart ran without an Enterprise license; nothing in these tests uses enterprise features.
- Dovecot's `service imap { vsz_limit }` is 2G, a tuned setting needed for 250k-message mailboxes (Dovecot's own message: "Out of memory (service imap { vsz_limit=256 MB }, you may need to increase it)"). Every large-mailbox test and the mixed IMAP test ran with it. All other tuning is in [SETTINGS.md](SETTINGS.md).
- Both sides log at info level to the OS disk, not the data disk: about 5 lines per inbound message on Stalwart, 6 to 8 on Postfix and Dovecot together. Stalwart's lines are longer: over about 13.4 hours of tests on one cluster, Stalwart wrote 2.38 GB of logs and Postfix + Dovecot 1.01 GB together, both at their default info level.
- At every start Stalwart tries to download its web admin bundle, which returns 404, and logs one ERROR line; nothing is measured during a start.

## 11. Errors that are not failures of the measured operation

In the large-mailbox COPY tests, a few Dovecot samples report an error that comes from the untimed cleanup after the COPY, which deletes the target folder: Dovecot answered "New mails were added to mailbox during deletion". The COPY latencies are valid and the errors are published as they are. The COPY tests on regular mailboxes with 16 sessions show the same pattern, at up to about 0.15% of samples (42 of about 30,000 on c14-sessions16-copy-one, 7 on c14-sessions16-copy-range100; Stalwart none): almost all are the same rejected cleanup DELETE, plus two I/O errors. In the `fsync=always` variant a few COPYs were rejected because the target folder did not exist (`TRYCREATE`). Each session uses its own accounts, so the sessions do not interfere; the likely cause is a lock-order conflict between the imap process and Dovecot's full-text indexer, which holds the fts-flatcurve index lock after each COPY or MOVE (section 3); this comes from the Dovecot logs and was not traced. In the diagnostic run with `fts_autoindex = no`, the 16-session MOVE test had no errors. The latencies of the successful operations are valid. Other errors (for example a few rejected or timed-out MOVEs of 10% of the 100k mailbox on Dovecot) are also published as measured. Every error is listed in [RESULTS.md, section 14](RESULTS.md#14-flags-cv-errors-incomplete-cells).

## 12. Storage use

Stalwart stores a message delivered to several recipients once; Dovecot's mdbox stores one copy per recipient. With 1 MB messages to 10 recipients over 16 connections, Dovecot wrote about 110 GB per repetition. That difference matters for anyone sizing storage; disk use was not measured systematically on both servers.
